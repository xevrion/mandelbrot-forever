what you're seeing: every pixel is a point c in the complex plane (left-right is the real part, up-down is the imaginary part). black means we iterated z = z2 + c and it never escaped, so it's in the set. colors mean it escaped, and the shade tells you how fast: points far from the set escape in a few steps, points hugging the edge take hundreds. detail is the max iterations before we give up and call a point black. deep zooms need more of it because points near the edge take longer to decide, so by default it rises on its own as you zoom (that's the auto button), and you can drag the slider to override it. shift rotates the colors through the palette live. the corner window is the julia set for wherever your mouse is, and every point in the complex plane has its own, so you're seeing an infinite family of fractals by just moving your hand. the hud shows zoom: 1x is the whole shape, and you can go to about a hundred million million million million x (1026) before the numbers run out of precision.

wait, what is this

this is the mandelbrot set, probably the most famous picture in all of math. the black shape in the middle is the set itself, and the colors around it show how quickly each point outside it "escapes". the wild part is the edge: no matter how far you zoom in, it never gets smooth. there are tiny copies of the whole shape hiding inside its own edge, forever. genuinely infinite detail from a formula you could write on a napkin.

and here's the thing that gets people: the formula is z = z2 + c. that's it. pick a point c, start z at zero, and keep squaring and adding. if z stays small forever, the point is in the set (black). if it blows up to infinity, it's outside, and the color tells you how many steps it took to blow up. every single pixel on screen is that one calculation, done hundreds or thousands of times.

how to explore: click anywhere to glide into that spot. scroll to zoom, drag to pan, pinch on a phone. hover and watch the little window in the corner, that's the julia set for the point under your cursor, a whole second fractal that changes as you move. try the bookmarked spots for the famous places. the url updates as you go, so copy it to share anywhere you find.

how it's actually built (the whole thing is one file)

this is the entire algorithm. for one pixel, given its point (cx, cy), count the steps until it escapes:

function escape(cx, cy, maxIter){
  let x=0, y=0, i=0;
  while(x*x + y*y <= 10000 && i < maxIter){
    const xt = x*x - y*y + cx;   // real part of z^2 + c
    y = 2*x*y + cy;              // imaginary part of z^2 + c
    x = xt; i++;
  }
  return i;
}

that's z = z2 + c written out with real and imaginary parts, because javascript has no complex number type. the escape test is the x*x + y*y check: once z gets further than 2 from the origin it is mathematically guaranteed to fly off to infinity, so we could stop right there. we let it run a bit further (to a radius of 100) because the smooth coloring below gets more accurate the further out you measure.

why the colors are smooth and not banded

if you color by the raw integer iteration count you get ugly hard stripes. the fix is smooth coloring: after the point escapes, look at how far past the bailout radius it overshot, and use that to add a fraction to the count. so instead of "escaped at step 37" you get "escaped at step 37.62", and that fractional part is what makes the gradients silky:

const log_zn = Math.log(x*x + y*y) / 2;
const nu = Math.log(log_zn / Math.LN2) / Math.LN2;
const smooth = i + 1 - nu;   // fractional iteration count

that number then picks a color from the palette. the palette is a loop, and the position in the loop comes from a mix of the log and the square root of the smooth count, which spreads the colors out so both the calm outside and the busy edge get a full range instead of one flat tone. the palettes themselves are blended in oklab rather than plain rgb, which is why the transitions don't go muddy or grey in the middle. the gpu samples the palette as a texture with linear filtering, so there is no lookup-table stepping at all.

how it runs on the gpu

every pixel is independent, which is exactly the kind of work a gpu eats for breakfast, so if your browser has webgl2 the whole image is a single fragment shader and a full frame usually takes a few milliseconds. that's why zooming feels like a video instead of a slideshow: every frame of the glide is a real render, not a stretched copy of the last one.

the catch is that gpus only do 32-bit floats, which run out of precision at about a hundred thousand times zoom. the trick that gets around it is called perturbation. the cpu computes one full orbit for the point at the center of the screen using 64-bit doubles, and uploads it to the gpu as a texture. each pixel then only tracks its tiny difference from that reference orbit, and the difference stays small enough for 32-bit math to handle:

// dz is this pixel's offset from the reference orbit Z, dc its offset from the reference point
dz = 2*Z[n]*dz + dz*dz + dc;      // same formula, expanded around the reference
z  = Z[n+1] + dz;                 // the real value is reference plus offset
if (|z| < |dz|) { dz = z; n = 0; }   // "rebasing": if the offset got bigger than the value, start over

that last line is the whole reason it works on a plain reference orbit with no glitch-fixing passes. when a pixel's orbit drifts away from the reference, it just re-anchors itself to the start of the orbit and carries on. the same idea is what real deep zoom programs use to go to 101000x, they just use arbitrary-precision numbers for the reference.

plain 64-bit doubles for the reference point run out at about 1013x, and you could feel it: panning would freeze because one pixel of movement was smaller than the gap between two representable numbers. so the center of the view is stored as a double-double, two floats stacked so the second one holds the rounding error of the first. that gives about 32 digits, which is enough for the reference orbit to stay honest out to roughly 1026x.

and when there is no gpu

if webgl2 isn't available (or the gpu bails out mid-session) the page falls back to plain javascript spread across web workers, one per cpu core, running the same math in doubles (the plain loop when shallow, perturbation once you are deep). the image is cut into horizontal strips of a few rows each and the workers pull strips off a shared queue, so a fast core just takes more strips. the main thread paints each strip as it lands, a quick low-res pass runs first so you see something instantly, and while you're moving it shows the last finished frame stretched to the new view so nothing ever tears. the little progress bar at the top of the image is the strips arriving. the render switch in the toolbar flips between the two live, so you can feel the difference yourself.

the julia set in the corner

the mandelbrot set asks "starting at z=0, does this c escape?" a julia set flips it: fix c, and ask for every starting z whether IT escapes. so every point c on the main image has its own julia set, and they're all different. points inside the mandelbrot set give connected julia sets, points outside give dust. hover along the edge and watch them morph, it's the same six lines of code with the roles of z and c swapped, running in its own little worker so it never gets in the way.

why it eventually breaks

the double-double trick buys about 32 digits, so somewhere past 1026x neighbouring pixels stop being distinguishable and you see blocks or noise. that's not the fractal ending, it's the number type running out. real deep-zoom software keeps the reference point in arbitrary-precision arithmetic (as many digits as the zoom needs) and goes to 10100x and beyond. that's on the try-later list.
